## How to Use (Agent Onboarding)

An owner installs and starts the desktop application, then configures a local Streamable HTTP MCP client using the current configuration generated by Hronaut Home. Follow https://hronaut.dev/setup. This is initial human setup, not autonomous URL registration.

After connecting, ask the agent: `Using Hronaut, create a new isolated workspace named “Hronaut first run”, open https://example.com, take a semantic snapshot, and tell me the page heading. Use only that task workspace.`

The default endpoint is local loopback. Hosted agents cannot reach it merely by reading the setup guide. Check https://hronaut.dev/client-topology for network-namespace boundaries. This entry does not require enabling LAN access or publishing a browser-control endpoint.

## What It Does

Hronaut is a visible desktop Chromium browser for coding agents. Named workspaces retain tabs, cookies and local storage across agent disconnects. The person can watch the browser, pause agent access and take over for manual steps.

It runs on Windows, macOS and Linux and automates pages inside Hronaut. It does not supply the coding agent or model, control native apps, or automatically attach an arbitrary existing Chrome profile. The public latest release observed September 30, 2026 was [v2.8.6](https://github.com/hronaut/hronaut/releases/tag/v2.8.6). Windows packages remain unsigned and macOS packages are not Apple-notarized; hashes and build attestations have a separate provenance scope.

The trial starts with the first agent tool call and lasts 10 consecutive days, with no card or automatic billing during trial. Ongoing use requires $4/month or $24/year per named user, up to three active devices. [Released terms](https://github.com/hronaut/hronaut/blob/v2.8.6/LICENSE).

## Primary Primitives

| Primitive | Description |
|---|---|
| **Task workspace** | Named local browser context with separate website storage |
| **Resumption capability** | Private capability for explicitly reconnecting to a persistent task workspace |
| **Write ownership** | Bounded transport lease; conflicts return BUSY without dispatch |
| **Semantic observation** | Page snapshots and current element references for targeted interactions |
| **Human handoff** | Visible pause and takeover for manual browser steps |

---

## Autonomy Model

1. The owner installs/runs the app and connects an appropriate MCP client.
2. The agent creates a fresh task workspace and opens a permitted public or localhost page.
3. The agent observes current page state and uses the exposed structured tools within its scope.
4. The agent reports the observed result; a dispatch response alone is not an independently verified postcondition.
5. The workspace persists after disconnect; a later client explicitly resumes it and inspects fresh state before reclaiming writes.

---

## Identity and Delegation Model

- Authority is locally delegated to connections and task workspaces, not an independent human/model identity attestation.
- Trusted settings can configure narrower capability profiles; an agent cannot mint its own authority.
- Pause, disconnect, authentication rotation, lease expiry and release revoke the transport's write authority. Pause does not roll back a dispatched action.
- Website storage is separated by workspace. Bookmarks, history, download records and remembered permissions remain application-wide.
- Optional audit recording has bounded coverage; do not assume always-on, all-tool auditing or independent security assurance.

## Human-in-the-Loop Support

The owner sees the same browser and can pause agents or take over for login, 2FA, CAPTCHA and consequential actions. These controls do not guarantee that every website or workflow can be completed unattended. Site and workspace restrictions still apply.

---

## Why Generic Alternatives Do Not Qualify

| Alternative | Why It Fails |
|---|---|
| **Stock human-facing desktop browser alone** | Ordinary tabs/profiles do not by themselves provide this task-owned MCP workspace/resumption contract |

Persistent profiles and automation are not unique to Hronaut. Playwright MCP and hosted browsers have valid alternative execution models. Hronaut's distinction is the local desktop workflow combining saved workspaces, browser tools and human controls.

---

## Use Cases

- **Local app QA** — inspect a localhost workflow with the coding agent already in use.
- **Signed-in app checks** — the person signs in; the agent continues inside the scoped workspace while the session remains valid.
- **Repeated development tasks** — explicitly resume the same browser context after agent disconnect.
- **Manual handoff** — pause, complete a manual step and resume after a fresh observation.
